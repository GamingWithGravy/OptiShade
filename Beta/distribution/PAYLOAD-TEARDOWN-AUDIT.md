# OptiShade manager payload teardown audit

This audit is for the local modular-launcher work. It records what the current manager carries, why it is present, and the conditions required before removing it. No game payload should be stripped from the local launcher until the replacement download, verification, install, repair, and uninstall path is complete.

## Current size baseline

The `installer/PayloadFusion` tree contains 261 files totaling 319,707,637 bytes (304.9 MiB). The current R381 executable is 296,325,120 bytes (282.6 MiB). Go embeds `PayloadFusion` through `all:PayloadFusion` in `installer/public_bundle.go`; the manager unpacks that embedded filesystem and starts `FusionSetup.exe` with the extracted `PayloadFusion` directory.

| Current payload category | Files | Uncompressed size |
| --- | ---: | ---: |
| Core | 148 | 43.59 MiB |
| Image Effects | 49 | 0.43 MiB |
| Neural Rendering | 24 | 81.23 MiB |
| Providers (FSR/XeSS) | 8 | 171.21 MiB |
| OptiMFG | 31 | 6.80 MiB |
| Glass Cockpit | 1 | 1.63 MiB |

Largest payload files include `libxess.dll` (74.19 MiB), AMD FSR frame generation (38.23 MiB), OptiScaler FP4 `weights.bin` (36.02 MiB), AMD FSR upscaler (27.43 MiB), XeSS Frame Generation (21.89 MiB), and the two loader-path copies of `winmm.dll` (26.24 MiB each).

The local signed package set now covers Core, Effects, OptiMFG, and Providers. The 8 provider DLLs are split into AMD FidelityFX and Intel XeSS archives, each below GitHub's 100 MiB ordinary-file limit. The existing user-facing Providers choice stages both signed packages and composes them into the current installer catalogue; the installer still owns and installs the same 8 provider paths as before. Neural Rendering and Glass Cockpit are not yet represented by local signed component packages. The local package verifier can assemble an install-shaped payload, but game install, repair, restore, and component lifecycle have not yet been validated from a payload-free manager. Removing the embedded payload from the normal build now would make those paths incomplete.

The live public `core-stable`, `effects-stable`, and `optimfg-stable` branches were also checked during this audit: each currently serves a `manifest.json` with `channel: download-only`, `installable: false`, and no publisher signature. The manager correctly refuses to install these files. A signed `channel.json` was not present on those branches at inspection time. This is a distribution readiness gap, not a downloader failure.

The local manager now has a separate signed-package staging action. It verifies the release signature, archive digest, every declared file's path/size/hash, and rejects symlinks, special entries, duplicate/unlisted/missing files, and over-limit expansion. It retains and revalidates the signed release manifest with the staged files. A verified Core plus selected signed components can be composed into the existing `PayloadFusion` layout and supplied to the running manager session; composition rejects mismatched compatibility contracts, missing dependencies, duplicate component selections, and conflicting file bytes. This gives the existing transactional game installer a verified payload source without changing its install logic. The stage/composition step still does not modify game folders. Unit tests exercise staging, cache reuse, tampering, traversal, links, hashes, incomplete inventories, composition, and contract conflicts. The live unsigned branches are deliberately refused by this path.

The Windows local-source smoke test has passed against the three locally signed Core, Effects, and OptiMFG candidates: package signatures and inventories were accepted, and the selected set composed into a valid install payload without touching a game folder. The selected signed package identities now persist in the per-user package cache; each manager launch can reconstruct the selected payload from cached signed stages without another download. Recomposition rechecks the signed file inventories and the current manager EXE's ProductVersion against each package's launcher range, so an incompatible manager falls back to the embedded payload. Regression tests cover cache creation, restart-style reconstruction, package tampering rejection, and reuse across a manager version still allowed by the signed range. This validates staging/composition only; it does not yet validate a game install, component upgrade, repair, rollback, restore, uninstall, or public GitHub fetch.

The currently staged `.tar.gz` packages use ordinary tar `./` root prefixes; Core and OptiMFG also contain `files.json` and `component-package.json`, while Effects contains the component catalogue but no `files.json`. The signed stager now normalizes safe leading `./` entries and permits only those two bounded, non-install package metadata files outside the signed install inventory. This preserves compatibility with the package layout without allowing arbitrary undeclared payload files. An end-to-end archive fixture covers that layout.

The signed staging command now receives the running manager's semantic version and enforces each signed release's `launcherRange` before downloading or extracting its archive. This closes a compatibility gap in the earlier staging prototype, which validated that the range was well formed but did not compare it with the active manager. It does not replace the missing component-to-Core API contract: independent future component updates still need a declared compatibility contract before the signed packages can be treated as production-ready.

The Core package's `files.json` is a Core-only install catalogue: 49 Effects files and all 31 OptiMFG files are not listed in it. A straight copy of that catalogue would therefore make the existing installer ignore those staged components. The local composer now extends the base catalogue with each selected component's signed file inventory, rejects any path whose declared bytes conflict with an existing Core entry, and then verifies all composed file hashes against the merged catalogue. The manager's staging selector only promotes a complete selected set; an unavailable selected package cannot silently fall back to Core.

Coverage check against the local 260-entry runtime catalogue: the three original staged packages covered 227 entries. The split provider packages now supply the 8 provider entries (171.21 MiB uncompressed; AMD archive 49,744,399 bytes, Intel archive 73,165,007 bytes), leaving 24 Neural files (81.23 MiB) and Glass Cockpit add-on (1.63 MiB) outside the local signed component set. Their source/licence and compatibility routes still need review. The full signed five-package stage has passed composition and includes both providers; its install lifecycle and cached byte-for-byte reconstruction must pass before the normal launcher can drop embedded files.

The full inventory of all 261 current payload files, with exact relative path, policy category, byte size, SHA-256, runtime role, compatibility risk, decision, and removal gate, is in [`PAYLOAD-TEARDOWN-INVENTORY.csv`](PAYLOAD-TEARDOWN-INVENTORY.csv). [`Build-PayloadTeardownInventory.ps1`](Build-PayloadTeardownInventory.ps1) rechecks every recorded size and hash against the local payload and regenerates the per-file review fields. It currently confirms all 261 entries match. Run it after any payload change; the hashes describe this local payload only.

The launcher embed inventory now also reads the PE machine field for every embedded EXE/DLL. The current scan found 44 x64 binaries and one x86 binary (`PayloadFusion/ReShade32.dll`); no invalid or unknown PE headers were found. The x86 ReShade file is an intentional 32-bit compatibility path and must stay paired with the x64 file unless 32-bit game support is explicitly retired. This is a static architecture check only: it does not prove Windows/API/GPU compatibility or that third-party code signing and runtime dependencies are correct. The removal audit must continue tracing call sites and validating each supported game/store/API route before changing the bundle.

This audit separates **bytes that can eventually leave the manager** from **files safe to delete from OptiShade**. The first-party provider and NR groups alone account for about 252.4 MiB (82.8% of the payload), but those features must remain available as optional, compatible downloads. The safe size saving comes from not embedding unselected components in the manager; it does not come from dropping feature support or deleting user/game files. Current removal decision for all 261 files: retain until the matching authenticated remote package is installed through every dependent lifecycle path.

## Teardown and compatibility decisions

| Payload | Keep/remove decision | Reason and risk | Safe removal gate |
| --- | --- | --- | --- |
| Core | Keep required files | Contains loader hooks, route DLLs, tools, scripts, headers, runtime metadata, and installation catalogue. `FusionSetup` and PowerShell install/update/repair paths read the extracted payload and `files.json`. Missing core files can break launch, install, repair, diagnostics, or uninstall ownership. | Publish a complete, hash-verified Core package; stage it locally; update all callers to use that staged root; prove install/repair/restore/uninstall work without the embedded copy. |
| Image Effects | Removable from manager EXE after online delivery is complete | Small payload (0.43 MiB) but still required for effects and the look editor. Missing FX assets or headers can cause compile/index failures such as effects remaining “installed, not loaded.” | Signed manifest and package include all runtime FX assets, headers and licenses; per-game install and repair can fetch/verify the package independently. |
| OptiMFG | Removable from manager EXE after online delivery is complete | 6.80 MiB. Runtime/helper, provider routing and supporting files must stay version-matched. Omitting helper/backend dependencies can turn a working live-control path into “waiting for game connection” or failed attach. | Independently versioned package and manifest, dependency/version checks, verified staging, and a tested upgrade/rollback path. |
| Neural Rendering | Do not remove until replaced by online provider/model packages | 81.23 MiB, including legacy loader paths, OptiScaler NVFP4 weights/cubins, and host-side files. Not every file is needed by every GPU/API/game, but a blanket removal would break supported routes and could regress MSFS or XP12. Model weights are version-coupled to the runtime. | Split by supported runtime/adapter/API only after reference and compatibility audit; publish each bounded package; select the matching package before installation; validate DLSS, XeSS/FSR and legacy paths per supported game. |
| FSR/XeSS Providers | Keep embedded in the normal launcher until the modular lifecycle passes; now staged through two local signed packages | 171.21 MiB uncompressed. These support non-NVIDIA provider routes and are represented in component policy. The existing Providers receipt/install/remove flow remains unchanged, and the modular manager currently fetches both AMD and Intel packages when that component is selected. | Verify signatures, hashes and inventories; test clean install, update, rollback, repair, restore, and uninstall across AMD, Intel and NVIDIA routes before removing embedded copies from the normal launcher. GPU/API filtering could reduce downloads, but must wait until backend requirements are fully mapped. Confirm publisher licence notices remain present in Core. |
| Glass Cockpit | Move to its existing official download/update route | 1.63 MiB. The update script already fetches the upstream asset, while a fresh install still relies on the embedded payload. Changing only one path risks “installed” state without the add-on actually present. | Make initial install, update, repair and removal use the same verified upstream release/version flow; retain clear source attribution and license. |

## Duplicate paths and apparent easy savings

The following files have identical SHA-256 contents at multiple paths:

- Root `winmm.dll` and `host64/winmm.dll` (26.24 MiB each).
- Root `ReShade64.dll` and `host64/dxgi.dll` (5.66 MiB each).
- `nvngx.dll_dlssnr.dll` also appears under `host64` (about 0.16 MiB).
- A few ReShade headers and license texts have duplicate contents.

These are not automatically safe to delete. They are installed under different filenames/paths for distinct loader or host processes; the game catalogue and relative-path installation logic depend on those paths. Go's embed/link process may share identical content internally, so deleting duplicate paths is unlikely to recover the full duplicated on-disk amount from the EXE. Keep both runtime paths unless the loader design changes and per-game compatibility checks prove one is unnecessary. Small duplicate license texts are a cleanup candidate only if the remaining notices still satisfy each upstream license and attribution requirement.

## Code coupling that must be removed before shrinking the manager

The embedded payload currently feeds multiple live workflows:

1. `public_bundle.go` embeds `PayloadFusion` into the Go binary.
2. `main.go` extracts the embedded bundle to a temporary/local runtime root.
3. `FusionSetup.cs` passes `<root>/PayloadFusion` as `-Payload`.
4. Setup, manager, component, auto-compatibility, ownership, repair, update, diagnostics and release-note scripts read payload files, `files.json`, and `OptiShadeData/BuildIdentity.json` from that root.
5. Packaging verification expects the complete payload and its catalogue.

Therefore the correct size reduction is to replace that implicit embedded source with an explicit local verified component cache, then make every workflow resolve the same staged payload root. The channel/signature verifier, package hashes, compatibility selector and transaction/rollback logic must reject incomplete or mismatched package sets before any game files change. Unsigned or download-only packages must remain non-installable.

## Follow-up implementation checklist

- Define a signed channel manifest per independent component; do not rely on branch names alone as trust or version proof.
- Add packages for all currently required categories, including Neural variants, and make Glass Cockpit installation/update consistent. Providers now has two locally signed channels; its transaction lifecycle remains a removal gate.
- Download to a temporary cache, enforce size bounds, verify signatures and per-file hashes, then atomically promote the complete package set. Only a complete verified composition may become the payload root used by the game transaction.
- Make Setup, repair, component manager, update, diagnostics and uninstaller consume the staged cache and its build identity instead of an embedded payload directory.
- Preserve offline repair/rollback behavior or clearly report when a component must be fetched again; never delete the only known-good backup before the new set verifies.
- Add architecture, GPU, graphics API and game compatibility metadata so unsupported large providers/models are not fetched or installed.
- Only after those gates pass, remove `all:PayloadFusion`, update package verification, and compare the resulting executable size and startup/install behavior.
- For each proposed removal, record the current file hash/size, its consumer, game/API/architecture/GPU compatibility, replacement package/version, failure fallback, and verification result. A file is not removable merely because its hash is duplicated, its UI option is hidden, or one game does not load it.
- Keep `FusionSetup`, runtime libraries required by the selected manager framework, updater/signature logic, uninstall/restore logic, and legally required notices unless a specific dependency audit proves replacement or removal is safe.

## Conclusion

The 200+ MiB size is mainly the embedded game payload, especially optional FSR/XeSS provider binaries and Neural Rendering/model assets. The manager code itself is not the main source of size. The safe path is to migrate each supported component to independently verified online packages and remove the embed only after every install and recovery path uses those packages. A premature embed removal would create a small launcher that can report success while leaving missing runtime files or broken recovery paths.

## Payload-free launcher size experiment

A separate local build tag, `optishade_modular`, keeps the manager scripts, host, UI, updater, diagnostics and support resources but excludes `PayloadFusion`; the normal R build still embeds that tree. The reproducible build entry point is `distribution/Build-ModularManager.ps1`. The current r5 provider-split candidate is 11,534,848 bytes (11.00 MiB), compared with the observed R381 EXE at 296,325,120 bytes (282.60 MiB): 284,790,272 bytes (96.11%) smaller. Its SHA-256 is `99D7FE31B6FDE365B885E8DAC2F35B09A97081F2179BB1E94D509183AF5AEB72`. r5 changes no game runtime bytes; it preserves the r4 payload-free startup, portable path, cache diagnostics and installed-component download fixes, and also suppresses per-game anti-cheat dialogs during an already approved whole-manager update batch. The startup smoke fixture now seeds consent only in its isolated test store. No graphics, store, API, GPU, or architecture compatibility resource was removed. The size data confirms that the game payload, rather than ordinary manager resources, drives the EXE size.

The first no-payload compatibility issue found was startup presentation: it read Core `BuildIdentity.json` before cached components were restored. Manager version and release notes now resolve from the running manager EXE, with Core identity optional and treated as separately versioned. The PowerShell 5.1 UTF-8 BOM is retained and the version fallback passed against the local R381 EXE. A second compatibility issue was found in portable mode: component workers enforced the installed app's `%LOCALAPPDATA%\\OptiShade\\Sessions` path even though portable builds use `Data\\Sessions`. Result-path validation now follows the running EXE's portable marker and the same `managerStore` resolution as startup. A third teardown-specific issue was inaccurate diagnostics: failed modular cache reconstruction claimed an embedded payload was still active, which is false in a payload-free EXE. Logging now distinguishes the full R fallback from the modular fail-closed state. The modular bundle test now checks that `PayloadFusion` is absent while the normal build still verifies every embedded payload hash.

The r5 candidate retains the signed-package stage/composition evidence established by the previous build: locally signed Core, Effects, OptiMFG, AMD-provider and Intel-provider packages in five selections: Core (148 files), Core+Effects (197), Core+OptiMFG (179), Core+Providers (156), and all components (236). Both split provider packages are staged when the existing logical Providers component is selected; all eight provider DLLs remain available. Cached all-components reconstruction matched all 236 file hashes, including deterministic `files.json`. No game directory was supplied or touched. Modular and full Go tests, `go vet` for both build tags, and a stripped Windows GUI build passed after directing Go temporary files to D: because C: had no free space.

This tagged EXE is a local integration candidate, not a tester build. Signed-package staging, selection, cache reconstruction, Go tests and vet have passed against local signed channel fixtures. A clean first-run GUI download from a remote branch and game install/update/repair/rollback/restore/uninstall have not been completed. A clean first run without cached packages needs online channel access; refresh must fail closed if access or signature validation fails. Neural Rendering, Glass Cockpit and legacy MFG are not represented by the current signed package set, so the modular build must continue to block those selections before game mutation. Component status also requires an online refresh; stale or unavailable catalogues must not be presented as proof of an installed component. The normal R build still embeds all 261 payload files. Keep the tagged EXE local and do not switch the public build until remote delivery and the full modular lifecycle gates pass.

## Expanded teardown review and uninstall safeguard

The owner asked that every size reduction be reviewed for its actual consumer, whether it is still required, compatibility effects, and failure/recovery behavior. `LAUNCHER-EMBED-AUDIT.md` records that review for non-payload resources, and `LAUNCHER-EMBED-INVENTORY.csv` records each embedded item, size and hash. The only content excluded from the 11.00 MiB candidate is the `PayloadFusion` tree: no individual runtime, helper, script, licence, or UI asset was removed. The helper/UI resource call sites were checked: FusionSetup is the WPF/PowerShell host, the troubleshooter is called by support actions, OptiShadeDriver is called by NVIDIA settings, the custom Fusion Cinema look is installed through recovery code, and manager scripts remain necessary for current workflows. The 1,011 KiB brand PNG could only be reduced safely with a separately verified lossless optimization and visual comparison; it was retained. The payload itself is not dead data: it includes game/API/GPU paths such as x86 ReShade, loader-specific duplicate DLL paths, optional FSR/XeSS providers, and neural models. These stay available in the normal build until their replacements and lifecycle paths are verified.

The uninstaller had another lifecycle gap found during this review: a fresh manager install with no game receipts was rejected even when its game index was genuinely empty. Cleanup now permits that specific case, while any remaining data under `Games` without a valid current receipt still stops removal and preserves backups. The dialog clarifies that unknown game files are never scanned/deleted. The canonical-cleanup fixture verifies both clean manager-only removal and that backup-only data still blocks cleanup; its 45 assertions pass. The AppData uninstaller's final cleanup was also exercised with temporary Windows directories: it removes the app/data roots and OptiShade shortcut files, removes the Start Menu folder only when empty, and leaves unrelated files intact. This does not replace interactive testing of the full wizard or alter game ownership validation, unavailable-game handling, original-file hash checks, or the restore-before-delete rule.
