# OptiShade modular delivery plan

Status: local preparation only. No GitHub branch, release, asset, or remote repository is created or changed by this document.

## Target layout

| Delivery unit | Owner | Update source | Installation owner |
|---|---|---|---|
| Bootstrap installer | OptiShade | The only asset attached to the public OptiShade release | Per-user installer; downloads and verifies the launcher |
| Launcher | OptiShade | `launcher-stable` or `launcher-beta` branch in the same repository | Per-user application directory; self-updates through a separate updater process |
| OptiShade core | OptiShade | `core-stable` or `core-beta` branch in the same repository | Existing per-game receipts, owned-file inventory, backup and restore transaction |
| OptiMFG | OptiShade | `optimfg-stable` or `optimfg-beta` branch in the same repository | Existing OptiMFG component receipt and runtime folder; migration adopts verified legacy copies |
| Image effects / Look editor payload | OptiShade | `effects-stable` or `effects-beta` branch in the same repository | Component receipt, effect-file inventory, and verified rollback |
| Optional FSR / XeSS providers | OptiShade package transport for licensed upstream binaries | `providers-amd-stable` and `providers-intel-stable` branches | Existing logical Providers receipt, ownership inventory, and verified rollback |
| Neural Rendering | Third-party/model sources | Existing pinned NVIDIA/model download method | Existing neural component path and installer safeguards |
| Glass Cockpit fix | IFreemz | Existing official GitHub release API and SHA-256 validation | Existing Glass Cockpit receipt and backup |
| AtmosphereMod | tomwhoca | Existing official GitHub release API and SHA-256 validation | Existing AtmosphereMod installer/receipt |

## User install and update flow

- Choosing **Install OptiShade** downloads and verifies Core only, then installs Core through the existing per-game backup and ownership transaction. It does not request AMD/Intel provider or other optional channels. Optional components are selected from the Components page after Core is verified.
- The Components page downloads only the selected first-party package(s). Glass Cockpit uses the Core baseline and then checks/updates from IFreemz's verified release; Neural Rendering and AtmosphereMod keep their existing publisher/model download routes. Update Manager refresh reads signed channel manifests only. Applying a first-party update stages Core plus that selected package; other components are not downloaded. A missing optional branch therefore cannot block Core or a different component's update. “Update all” still processes each available row separately and records individual failures.
- The manual “Online component packages” download/stage test card has been removed. It was a developer staging tool and confused the install flow. Signed manifest/package verification remains part of actual Core and optional-component installs.
- The download-only `manifest.json` fallback is not install authorization. Each production component needs a signed, installable `channel.json`; the current local Core package passes signature, hash, and composition verification. The public Core branch shown in the tester error is still unsigned/download-only, so a real online install remains blocked until that branch is replaced with the signed installable channel. No game files are changed on this failure.

The public Releases page remains reserved for the bootstrap installer. Each component channel uses a small `channel.json` and ordinary files on its branch. Packages are downloaded directly from `raw.githubusercontent.com`, then checked against the declared byte count, SHA-256, publisher signature and per-file inventory. Keep every package below GitHub's 100 MiB per-file limit; if a component grows beyond that, split it into independently declared component packages rather than requiring Git LFS. The launcher-channel generator now also keeps its EXE as an ordinary GitHub file: a previous generated `.gitattributes` rule forced EXEs into LFS even though both downloader paths use raw branch-file URLs and do not resolve LFS objects. That mismatch is removed and a 99 MiB generator guard prevents preparing an incompatible package. The current Core (14.27 MB), Image Effects (0.31 MB), OptiMFG (2.92 MB), AMD provider (49.74 MB), Intel provider (73.17 MB) and manager (11.06 MiB) packages fit as regular files. The user-facing Providers choice downloads both split provider packages and composes them under the existing installer component; no game-side component model changed.

### Launcher size and compatibility teardown requirement

For every further file considered for removal from the manager EXE, record its embedded bytes, runtime consumer/call sites, whether it is still required, and the Windows/game/store/graphics-API/GPU/architecture compatibility paths it supports. A smaller file is not automatically dead code. Retain a file unless a verified replacement is already used by setup, update, repair, recovery and uninstall and the affected route has regression coverage. After each approved removal, rebuild and compare manager size, run focused tests, and check the complete embed inventory for missing or orphaned resources. The current proven large reduction is the `PayloadFusion` exclusion in the local `optishade_modular` build: 319,707,637 source bytes (304.9 MiB) were excluded, reducing the observed executable from 282.60 MiB to 11.05 MiB while retaining about 3.6 MiB of launcher UI, scripts, helpers and branding. The reproducible r9 manager is 11,588,608 bytes, SHA-256 `6E4E1F2620F6B092E439EA66F4C84B356867215DC7762FE544C56BC2883CF74F` (96.09% smaller than R381). The retired download-only test command and its cache helper were removed after confirming they had no production callers; the signed staging command remains required for Core and optional component installation. No compatibility payload, architecture path, helper used by the UI, or licence file was removed. No additional launcher resource has been removed: the largest are active branding (about 1.0 MiB), troubleshooting and NVIDIA helper executables (about 0.9 MiB combined), and manager scripts/UI (about 1.4 MiB); deleting these has materially less impact and risks breaking visible features or compatibility routes. The refreshed per-file CSV inventories contain current sizes and hashes; they are not permission to remove a file without the call-site and compatibility review above.

## Package and trust contract

Each first-party manifest must include schema, product/component ID, semantic version, channel, architecture, minimum and maximum compatible launcher versions, required bridge/protocol contracts, dependencies, conflicts, package byte length, SHA-256, and an offline publisher signature. Git LFS identity is optional and unnecessary for normal-sized component archives. The launcher embeds only the public verification key. The signing key stays outside the repository and build machine artifacts; HTTPS and SHA-256 are transport/integrity checks, while the publisher signature establishes release authenticity.

Package paths are relative to a declared install root. Reject rooted paths, traversal, reparse points, duplicate paths, undeclared files, oversized archives, incompatible contracts, and unknown schema versions. The local schema-2 package planner is currently read-only; activating remote packages requires a reviewed transactional apply path and regression tests. Do not route a remote archive through the local schema-1 mutation entry point.

## Update and rollback flow

1. Fetch the channel manifest over HTTPS with bounded time, response and redirect limits.
2. Verify manifest signature, version ordering, compatibility contracts, package digest, byte count and package inventory.
3. Build a read-only plan for every selected game and component. Revalidate the game executable, receipt fingerprint, anti-cheat status and current owned-file hashes at mutation time.
4. Ask once for consent when a batch includes a game with detected or possible anti-cheat. Do not let unrelated dialogs overlap the operation window.
5. Stage the complete package away from the game. Back up every replaced owned file and the exact prior receipt in a transaction journal. Never overwrite a foreign or changed file.
6. Apply files, verify the installed hashes, then commit the component receipt. If any step fails, restore verified backups and the prior receipt before reporting failure.
7. Keep a verified prior package/receipt for one-click component rollback. Full uninstall restores only files and settings with matching OptiShade ownership evidence; preserve user presets and foreign files.

Core, OptiMFG, and effects get independent version rows. Dependency or ABI changes that cannot be mixed safely must be declared as one atomic update set and applied or rolled back together. Neural Rendering, Glass Cockpit and AtmosphereMod keep their current publisher-specific update methods.

Legacy migration must inventory installed files and current receipts before writing to the new component folders. A verified old OptiMFG runtime is adopted or transactionally moved, never copied alongside a second active runtime. If ownership is uncertain, stop and leave files untouched for review.

## Installer and launcher lifecycle

- The intended bootstrapper contains no launcher/game payload. It downloads the signed launcher package as an ordinary GitHub branch file (under 100 MiB), verifies it, installs into a per-user OptiShade application directory, and offers desktop/start-menu shortcuts.
- A local Windows bootstrapper prototype now exists at `Beta/distribution/bootstrapper/`. It pins the same-repository `launcher-stable` branch, checks an Ed25519-signed `channel.json`, downloads a SHA-256-checked ordinary branch file capped at 99 MiB, installs under `%LOCALAPPDATA%\Programs\OptiShade`, and uses a local ownership receipt plus a `.previous` recovery copy. The manager must first stop embedding `PayloadFusion` so its launcher package fits this transport.
- `bootstrapper/build.ps1` builds the installer locally. Its first run creates an Ed25519 private key under `%LOCALAPPDATA%\OptiShade\Distribution\release-ed25519-private.pem` and stores only the public key in `Beta/distribution/release-public-key.json`. Keep the private key out of GitHub branches and source control; configure it as a protected GitHub Actions secret only when release workflows are authorized.
- The normal launcher remains separately updateable. A helper stages and verifies its replacement, waits for the running process to exit, swaps atomically, and retains the prior verified launcher for rollback.
- Terms and the anti-cheat warning are shown before the first game mutation. Record the accepted terms version and timestamp locally; per-game detection still runs immediately before installation.
- “Start with Windows” is an opt-in per-user startup entry. The manager now starts with `--tray`, hides its window, keeps its update polling active, offers Open / Update Manager / Exit in the tray menu, and raises a Windows balloon notification when the existing managed-update poll discovers an available update. This is implemented locally; notification behaviour and lifecycle still need interactive validation before release.
- The app migrates an existing OptiShade startup entry to the current manager path and tray mode when its settings are opened. Startup remains opt-in; no startup entry is created for users who have not enabled it.

## Diagnostics defaults and privacy

- Suspected game-stall reports default to automatic private upload. They contain bounded logs and thread-stack evidence, not a full live-process memory dump. Users can switch automatic upload off; failed uploads remain local for retry.
- Windows LocalDumps is requested per game during OptiShade installation and requires the user to approve the Windows elevation prompt. Raw crash dumps contain process memory; keep them local unless the user chooses to include them in a report. Never silently attach raw dumps to an automatic hang upload.
- A report must show the report ID and upload status. Do not upload crash data until relay confirmation; retain local copies on failure.

## Where each piece goes on the public repository

Publishing is a separate, owner-approved step. Each unit is published and updated on its own:

| Piece | Public location | What a change there does |
|---|---|---|
| Bootstrap installer | The Release attached to `GamingWithGravy/OptiShade` (the only Release asset) | New installs only; existing users are not affected |
| Launcher (manager EXE) | `launcher-stable` branch: signed `channel.json` plus the package file | Installed launchers offer a self-update; the previous EXE is kept for recovery |
| Core | `core-stable` branch: signed `channel.json`, `packages/OptiShade.Core-<version>.tar.gz` | Update Manager offers a Core update per game |
| OptiMFG | `optimfg-stable` branch | Update Manager offers an OptiMFG update only |
| Image effects | `effects-stable` branch | Update Manager offers an Effects update only |
| AMD / Intel providers | `providers-amd-stable`, `providers-intel-stable` branches | Not published yet; the channel check reports them as unavailable |
| Developer message | `main` branch: `developer-message.json` | Launchers show the new text within about 30 minutes (GitHub's raw cache can add about 5) |

A component update is only offered when its signed version is higher than the installed one, so every republished fix needs its own version bump. Every `channel.json` must be signed with the `optishade-release-2026` key that installed launchers trust; a different key is rejected.
